# 决策记录（DECISIONS）

规则：影响架构、依赖、协议、验收口径的决策都记一条；一行现状 + 一行理由。修改既有决策 = 新增条目并标注取代关系，不改历史。

- **D-001 播放内核 = libmpv。** ffmpeg 生态 + gpu-next 渲染，seek/截图/HDR/独占输出全覆盖；PotPlayer 闭源不可用，自研解码链违反铁律 #1。
- **D-002 菜单策略 = 虚拟菜单优先，BD-J 列 P3 评估。** 演唱会碟菜单本质是选曲；MusicDisc 数据可做出优于原生菜单的体验。开源 BD-J 仅 libbluray+JVM 一条路，兼容性天花板即 VLC/Kodi，不值得阻塞主线。
- **D-003 明确不做解密。** 只支持已解密资源，绕开 AACS/CSS 的法律与工程复杂度；加密盘给明确报错。
- **D-004 License = GPL-2.0-or-later。** 依赖链（mpv 默认构建、libdvdread、scarletbook 血统代码）均为 GPL 系；项目本身定位社区工具，开源为正资产。
- **D-005 UI = Qt 6 Quick，渲染强制 OpenGL RHI。** mpv render API 需要 GL；Metal 默认路径不可用（CLAUDE.md 深坑 #1）。
- **D-006 SACD 解码隔离在独立 helper 进程。** GPL vendored 代码物理隔离、崩溃隔离、协议清晰（ARCHITECTURE §SACD）。
- **D-007 开发与 M1 验收平台 = macOS；Windows 走 T8 构建通道、M2 打包首发。** 开发机为 macOS；Qt+libmpv 栈双平台同源。
- **D-008 碟片指纹 v1 规范冻结。** 见 ARCHITECTURE §指纹；发布后不可变，演进走 v2 双写。
- **D-009 libmpv = 自编译到 `third_party/prefix`（取代系统 Homebrew 版）。** Homebrew 的 mpv 0.41.0 编入了 libbluray（`bd://` [OK]）但**未编入 dvdnav**（`dvd://` 缺失），而 M1 T4 必须走 `dvd://<title>`，故按 CLAUDE.md 深坑 #3 用 meson 自编译，`-Dlibbluray=enabled -Ddvdnav=enabled`，探测结果转为 `bd://` 与 `dvd://` 双 [OK]。CMakeLists 已实现 prefix 优先于系统的 pkg-config/CMake 查找；重建脚本见 `scripts/build-deps.sh`。**交叉验证**：GitHub Actions macos-14 干净 runner 上（run 32915478493）同一脚本独立复现出 `bd://` [OK] / `dvd://` 缺失，确认这是 Homebrew mpv 的构建口径而非本机环境问题。
- **D-010 T0 骨架不打成 macOS .app bundle。** M1-PLAN T0 验收口径是 `./build/md-player` 直接出窗口，故 `MACOSX_BUNDLE FALSE` + 产物落 build 根；正式打包形态放 M2（Windows 首发打包一并处理）。
- **D-011 DVD 栈（libdvdread + libdvdnav）一并自编译，且 `-Dlibdvdcss=disabled`。** Homebrew 的 libdvdread 把 **libdvdcss 编成硬加载项**（`LC_LOAD_DYLIB`，非 dlopen），libdvdnav 依赖它，链条 libmpv → libdvdnav → libdvdread → libdvdcss 会让解密库随进程启动被加载，直接违反铁律 #2。故在 prefix 内重建两库并关闭该选项；递归依赖闭包扫描 46 个库，确认无 libdvdcss / libaacs / libbdplus。**残留说明**：关闭链接后 libdvdread 上游仍保留运行时 `dlopen("libdvdcss.2.dylib")` 兜底分支，我们既不链接也不分发该库，用户自行安装属其自身行为；如需彻底铲除需 patch 上游源码，见【待决策】。
- **D-012 libdvdcss 立场固化：不链接、不携带、不 patch 上游。** 取代 D-011 的【残留说明】部分（D-011 其余内容仍有效）。三条约束：(1) 自编译 libdvdread 一律 `-Dlibdvdcss=disabled`，任何平台的分发包都**不携带** libdvdcss；(2) **不对上游源码做任何 patch**，其运行时 `dlopen` 兜底分支原样保留，维护成本为零；(3) 用户自行安装 libdvdcss 属其自身行为，**加密盘行为的确定性由应用层保证**——DVD 模块自检扰码位并主动拦截，不依赖底层库是否恰好解不开。验收口径见 M1-PLAN T4。

- **D-013 demuxer 缓存维持 `demuxer-max-bytes=768MiB` / `demuxer-max-back-bytes=512MiB`，不为 UHD 上调。** T2 在 83.2 Mbps 的 4K HEVC 原盘流上实测：拖动中位到位 41ms、19 次采样 18 次 <100ms，手感与 42.9 Mbps 1080p 样本（中位 43ms）基本一致，**大缓存 + keyframes seek 的配方在 UHD 码率下依然成立**，没有上调的必要性。已知代价：83 Mbps 下 512MiB 回退窗口仅覆盖约 **49 秒**，超出该窗口的大幅**向后**拖动会退化为落盘重读，实测偶发 ~200ms 级延迟（T2 中出现 1/19 次，222ms）。此现象**定性为已知特性**，不作为缺陷。**约束：今后任何缓存参数改动，必须重跑 T2 的 seek 基准并与本条记录的数字对比后方可提交**（拖动节流违反次数、到位耗时最小/中位/最大、<100ms 占比）。
- **D-014 蓝光标题列表 = `TITLES_RELEVANT` 且不做时长过滤，按 libbluray 枚举顺序展示，主标题只加徽标不重排。** `TITLES_RELEVANT`（= 去重复标题 + 去重复 clip）能滤掉混淆用 playlist，但**不能**再叠加最短时长过滤：演唱会碟常把曲目组拆成多条短 playlist，滤掉就等于丢内容（ARCHITECTURE §bluray「始终同时展示完整列表」）。代价是 UHD 原盘的一堆 5 秒占位 playlist 也会列出来（THE WARNING 那张 11 条里有 5 条是 5 秒），用主标题徽标 + 打开即播主标题来抵消。**不按时长排序**：那会打乱演唱会碟的曲目顺序，比列出几条占位项更糟。
- **D-015 libbluray 的 1.5 新能力必须「编译期宏 + `bd_get_version()` 运行时版本」双重把关。** 章节名（`BLURAY_TITLE_CHAPTER::chapter_name`）与 HDR 元数据（`BLURAY_STREAM_INFO::dynamic_range_type`）都是**结构体成员**而非函数，无法用 dlsym 探测；对着 1.5 头文件编译却链接到 1.4 运行库时读它们会越过实际分配的内存。故 `BlurayDisc.cpp` 两道关同时卡，任一不满足即降级（章节名→「第 N 章」，HDR→不显示）。**实测**：REJOICE_BONUS 与 THE WARNING 两张样本碟内均无 META TOC，章节名 0 条，走的正是降级路径。
- **D-016 加密判定排在 `bluray_detected` 之前。** 加密盘的 `index.bdmv` 本身不加密、通常能解析，但一旦某张盘结构解析失败，先报「不是蓝光」会把用户引向完全错误的方向。故 `aacs_detected && !aacs_handled`（BD+ 同理）一命中就立刻返回 Encrypted。验证手段见 `tests/fixtures/make_bd_skeleton.py --aacs`——自造骨架即可让 libbluray 报 `aacs_detected=1 / aacs_handled=0`，不需要真加密盘。
- **D-017 碟类资源的断点键 = `<碟根>#<URI>`，不是 URI 本身。** `bd://mpls/1` 在任何一张碟上都长一样，直接拿它做 ResumeStore 的键会让不同碟共用同一条断点记录，续播跳到毫不相干的位置。普通文件仍以路径为键，行为不变。
- **D-018 覆盖在播放画面上的面板一律 `focus: false`，键盘关闭改用窗口级 `Shortcut`。** Qt Quick 的 Popup 一旦拿到 activeFocus，`QQuickPopupItem` 就会成为窗口的 `activeFocusItem`，此后窗口级 `Shortcut` 即便 `enabled === true` 也**永不触发**——T3 的标题面板一开，空格 / 方向键 / 截图快捷键全哑（实测 `activeFocusItem=QQuickPopupItem("TitlePanel")`，改 `focus: false` 后回到 `QQuickRootItem("Main")`，快捷键立即恢复）。代价是 `Popup.CloseOnEscape` 随焦点一起失效，Esc 关闭改由窗口级 Shortcut 承担（正因为焦点没被抢走，它才触发得了）。**播放器的键盘手感优先于面板的焦点导航**，后续任何叠加面板都按此办理。同一机制也是 issue #1（续播框回车失效）的根因线索。
- **D-019 标题列表加「隐藏 10 秒以下条目」开关，默认开启，只隐藏不删除。** D-014 定的「不做时长过滤」保证了数据层的完整性，但展示层需要一个出口：UHD 原盘的占位 playlist（THE WARNING 那张 11 条里 5 条是 5 秒）混在列表里纯属噪音。故过滤只发生在展示层——`BlurayController::playlists` 始终是碟内**完整**结构（Studio 模式将来要按完整结构做曲目编排），面板读的是过滤后的 `visiblePlaylists`，每个条目自带碟内原始下标 `index`，播放与高亮一律按原始下标走。**两条永不隐藏**：主标题、以及当前正在播放的那条（否则会出现「在播的标题不在列表里」的怪状态）。阈值 10 秒硬编码在 `kShortTitleSeconds`，开关状态存 `QSettings("ui/hideShortTitles")`，默认 true。
- **D-020 打开碟不自动弹标题面板，改为播主标题 + 每次会话一次的上手提示。** 面板是左侧抽屉，宽度约占窗口 1/3，自动弹出会立刻遮住刚开始播的画面，而「打开碟就是想看主标题」才是绝大多数场景。故打开碟只做两件事：播主标题、弹「已载入蓝光碟：X（N 条标题）」提示条。面板入口保留两个常驻通道：播控条的 ☰ 按钮（碟类资源才出现）与快捷键 `T`。**上手提示按会话计**：每次启动后打开的**第一张**碟，在碟名提示淡出后补一条「按 T 选择标题 / 章节」，同一次运行内不再重复。状态是进程内的一个静态标志，**不落盘**——曾用 `QSettings("ui/titleHintShown")` 做成「装了之后永远只提示一次」，但这条提示的作用是唤醒记忆而不是教学，隔几周再打开时用户同样需要它；按会话计既保证同一次使用里零重复打扰，又不至于让人永久失去线索。面板入口（☰ 与 `T`）本就常驻，提示只是补充。
- **D-021 DVD 播放定位符 = `dvd://<titleNumber-1>`，即 mpv 侧 0 起编号。** libdvdread 的 title 是 1 起（`tt_srpt` 顺序），mpv 的 `dvd://N` 是 0 起，换算在 `PlayerController::loadDvd` 一处完成。**实测确认**：`dvd://2` 落在 libdvdread 的 title 3 上，且与 `--edition=2` 完全等价——mpv 的 dvdnav 把整张碟当作一个文件、把各 title 暴露为 edition，`dvd://N` 只是开场即切到第 N+1 个 title 的语法糖。七条 title 的时长与 libdvdread 解出的值逐条吻合（02:00:49 / 14.0 / 108.0 / 5.667 / 21.0 / 30.5 / 21.0 秒）。
- **D-022 DVD 加密拦截 = 应用层读 VOB 扇区自检 PES 扰码位，且判定排在结构解析结论之前。** 落实 D-012「加密盘行为的确定性由应用层保证」。位置**已实测确认**为 M1-PLAN 所给的参考位置：DVD 的 pack 头恒为 14 字节无填充，紧随其后的 PES 头 flags 字节落在扇区偏移 `0x14`，其 bit5..4 即 `PES_scrambling_control`。每个 title set 采样 32 个扇区、最多探 4 个 title set，只统计 pack 头开头且 stream id 为 `0xBD` 或 `0xC0..0xEF` 的扇区（导航包 `0xBB/0xBF` 不带该字节）。**实测**：三张已解密真盘 8 个 title set 共 100+ 个 PES 扇区全部为 0；自造加扰骨架 32/32 命中并给出统一文案。顺序上与蓝光侧 D-016 同口径——先判加密，再判「结构读不了」，否则加密盘会被误报成损坏盘。**本函数只读原始扇区看两个比特，不做任何解密。**
- **D-023 DVD 的音轨 / 字幕按 PGC 的 `audio_control` / `subp_control` 可用位过滤，面板摘要不显示声道数。** `vtsi_mat->nr_of_vts_audio_streams` 是该 title set 的**上限**而非某条 title 实有的流数：张学友那张碟声明 8 音轨 / 32 字幕，mpv 实际只有 4 音轨 / 0 字幕，多出来的条目 attr 里全是垃圾值。真实可用性写在 PGC 的 `audio_control[i] & 0x8000` 与 `subp_control[i] & 0x80000000` 上，按它过滤后与 mpv 逐条对齐。另：`audio_attr.channels` 本身也不可靠（同一张碟的 DTS 轨 IFO 写 5 声道、实际码流 6 声道），故面板摘要只列编解码器，声道数以播控条上由 mpv 提供的音轨列表为准——与蓝光侧口径一致。
- **D-024 碟片指纹 v1 的字节拼法就此钉死。** ARCHITECTURE 只写了拼接的成分，具体编码必须落到字节才可复现，故在此固定，改动等于换指纹（只能新增 v2 并双写）。**蓝光**：`index.bdmv` 全文 ∥ `MovieObject.bdmv` 全文（缺失按空串参与，纯 BD-J 碟见过缺的）∥ 按文件名升序的每个 `BDMV/PLAYLIST/*.mpls` 的（文件名 UTF-8 字节 ∥ 文件大小的十进制 ASCII ∥ 该文件全文的 sha256 **32 字节裸值**），三段之间不插分隔符。文件经 `bd_read_file` / `bd_open_dir` 读取，**目录与 ISO 走同一条路径**。**DVD**：`VIDEO_TS.IFO` 全文 ∥ 按 title set 编号升序的每个 `VTS_xx_0.IFO` 的 sha256 裸值；title set 数取自解析后的 VMG（`vmg_nr_of_title_sets`），不去猜 1..99。**SACD**：LSN 510 起 10 个扇区（scarletbook 的 `START_OF_MASTER_TOC` / `MASTER_TOC_LEN`）的原始字节——SACDText 区块本就在这 10 个扇区内，整块参与即可，不必把 scarletbook 结构体提前拉进 M1。输出为小写十六进制。**实测**：同一张 DVD 放在四个不同路径（原目录、直接拖 VIDEO_TS、套 2 层、套 3 层）下算出的指纹完全相同（`1ceef8a3…`），六张碟两两不同。M1 只落日志，**不做任何网络上行**。
- **D-025 碟根下探：深度上限 3 层，命中即停，多候选一律报错。** 从拖入目录算起，碟根最深可在第 3 层被找到（实测：第 2、3 层能找到，第 4 层找不到）。命中 `BDMV/index.bdmv` 或 `VIDEO_TS/VIDEO_TS.IFO` 的目录、以及 `.iso` / `.img` 文件都算候选；判定看的是**结构文件**而非目录名——只有空 `VIDEO_TS` 目录的残缺资源相当常见，那不该被收下再在打开时报错。递归遇到 `BDMV` / `VIDEO_TS` / `CERTIFICATE` / `AUDIO_TS` 即停止下钻，不进碟内扫描（UHD 原盘上很慢且没有意义）。**恰好一个候选就直接打开；两个及以上一律报错让用户指定，绝不替他挑一张。** 提示条只列碟名不列相对路径——王菲那套四碟的相对路径每条一百多字符，拼出来比窗口还宽，反而认不出哪张是哪张。
- **D-026 镜像完整性只比对「结构声明的总大小」与「文件实际大小」，不抽扇区试读。** 试读失败在真盘上会误伤（划痕、慢速光驱、网络挂载），而截断镜像的特征恰恰是「头部结构完好、尾部内容缺失」，用声明值一比即知。两条路线：有 ISO9660 主卷描述符（DVD / SACD 镜像）就比 `volume space size × logical block size`；纯 UDF 镜像（蓝光原盘常见，无 ISO9660 桥）则看 UDF 规定的「LSN 256 与卷末各有一个锚点描述符」——头部锚点在、卷末锚点不在即为截断。两者都不成立时**不下结论**，交给后面的模块判，别在这里冒充「截断」。**实测**：六张真镜像（DVD×2、BD×3、SACD×1）全部判为完整，各截到 8MiB 后全部当场拦下；自造的两个骨架（`make_broken_iso.py`）覆盖两条路线，不含任何版权内容。判定发生在**打开阶段**，不会先列出标题再在播放时失败。
- **D-027 SACD 在 M1 只识别不播放，且不落到 mpv 的英文原文。** 按 ARCHITECTURE 判定表，`.iso` 先查 `510*2048` 处的 `SACDMTOC` 签名，命中即判为 SACD，给「识别到 SACD 碟，播放支持将在后续版本提供」并把指纹写进日志。此前 SACD ISO 会一路落到普通播放、由 mpv 报一句英文 `unrecognized file format`——识别得出却说不清楚，比不认识更糟。播放实现归 T6。
- **D-028 截断判定改用文件系统级声明，取代 M1-PLAN T5 括号里建议的「DVD 看 VOB last sector、蓝光看 m2ts clip 长度」。** 补充 D-026 的选型理由。括号建议要走应用层结构解析：DVD 得逐个 IFO 解 `vts_ptt_srpt` / cell playback 表求出最末 VOB 扇区，蓝光得逐条 mpls 解 clip 的 SPN 区间再回查 clpi——两条路都得**先把碟解析成功**才谈得上校验，而截断镜像恰恰可能在解析阶段就崩在半路（T4 实测的 8MiB 截断件 IFO 还读得出来，是运气不是规律），且这套解析对 UHD 原盘慢得离谱。文件系统层的声明值（ISO9660 主卷描述符的 `volume space size × logical block size`；纯 UDF 镜像的卷末锚点）位置固定、读两三个扇区就有结论、且**先于**任何碟结构解析，正好卡在「打开阶段就判死」这个验收要求上。两种口径的目标一致（都是问「文件尾巴还在不在」），文件系统层是更浅也更早的那一层，故取代之。
- **D-029 D-026 的已知误伤面 = 非规范 UDF 镜像，收窄逻辑三重。** UDF 规范要求卷末（或倒数第 256 扇区）必有锚点描述符，但这是**规范约定**，个别刻录/转储工具产出的镜像可能不满足，此时完整镜像会被误判为截断。收窄做法：(1) 只在**头部锚点存在**（LSN 256 命中）时才允许下「截断」结论——连头部锚点都没有说明这根本不是 UDF 镜像，不归本判定管；(2) 卷末与倒数第 256 扇区**任一命中即放行**，覆盖规范允许的两种摆放；(3) ISO9660 与 UDF 两条路线都不成立时**不下结论**，交给后面的模块判，不冒充「截断」。实测六张真镜像（DVD×2 / BD×3 / SACD×1）零误伤。若日后出现误伤实例，处置方向是加一条「用户强制打开」的逃生口，**不是**放宽判定——放宽等于把 T4 那个「先列标题、播放时才失败」的缺口重新打开。

- **D-036 SACDText 由 helper 原样吐字节 + 字符集编号，转码在 Qt 侧做。** helper 是 C 进程，要在 macOS 与 Windows 上都把 Music Shift-JIS / GB2312 / Big5 / KSC5601 转成 UTF-8，就得带 iconv（LGPL-2 的 `charset.c` + 平台差异 shim）；而 Qt 侧本来就有 `QStringDecoder`，双平台同一套。故 `open` 响应里的文本字段一律是 `*_b64`（碟内原始字节的 base64），另给 `charset` 字段（碟内 `character_set_t` 编号），播放器侧解码，不认的编码降级 `Track N`。vendored 的 `charset_convert()` 用一个 30 行直通 shim 顶掉（只复制字节、补 NUL，不转码）。**这是协议 v1 首个实现落地前的设计定稿，不是破坏性变更**——协议 v1 此前没有任何实现，`ARCHITECTURE §SACD` 的字段表同步修订即可；本项目明文冻结、发布后不可变更的只有**碟片指纹规范（D-008 / D-024）**。**指纹不受影响**：SACD 指纹哈希的是 LSN 510 起 10 个扇区的原始字节，与文本怎么呈现无关；受影响的只有日志里的 `label` 字段（阶段 2 从 ISO9660 卷标升级为专辑名时会变，那是显示值不是哈希值）。
- **D-037 ffmpeg 的 DST 解码器方案正式关闭，DST 一律在 helper 内解成裸 DSD。** 理由是架构而非重量：**DST 是变码率的**，一旦把 DST 码流透传给播放器，`dsf_size` 就不再可预先计算、`offset → 时间` 也不再是线性映射，而这两条恰恰是协议 v1 里 `stat` / `read` 的立身之本（seek 要落点、mpv 的 stream_cb 要 size）。更要命的是 DSD 轨与 DST 轨会就此分裂成两条代码路径——一条线性、一条要查索引，seek、缓存、时长换算全部得写两遍。helper 内解码则让**每条轨在 mpv 眼里完全同构**：都是一个尺寸已知、偏移线性的 DSF 文件，DSD 与 DST 的差别只剩「怎么拿到那串字节」这一层，封在 helper 里。另：DSF 容器规范本身也不支持 DST，透传方案还得换 DSDIFF 容器，等于把协议 v1 推倒重来。
- **D-038 DSF 视图的尺寸由「碟内声明时长 × 声道数」推出，多退少补。** SACD 的时间基是 1/75 秒，每帧每声道恰好 4704 字节（588 样本 × 64fs ÷ 8），于是 `每声道字节数 = 时长帧数 × 4704` 是精确整数，`dsf_size = 92 + ceil(每声道字节数 / 4096) × 4096 × 声道数`。实际解出来的音频字节可能与这个数略有出入（碟上帧的边界与曲目时间码不总是严丝合缝），一律以声明值为准：多出来的帧丢弃，不足的补 `0x00`（DSF 规范的填充值）。这样 `stat` 才能在**读任何音频之前**给出精确尺寸，`read` 才能对同一 `(area,track)` 逐字节可复现——两者都是协议 v1 的硬要求。实测：手头 7 张碟（4 张纯 DSD + 3 张 DST，含 6 声道区）两次 `stat`/`read` 全部逐字节一致；导出的完整 DSF 经 ffprobe 识别为 `dsd_lsbf_planar`，时长与碟内声明相差 < 6 毫秒（即最后一个 4096 字节块的补零）。
- **D-039 DSD 位序与声道排布：碟内 MSB first、按字节轮转；DSF 要 LSB first、按 4096 字节/声道 分块。** 两者之间是一次逐字节比特翻转加一次纯排列，没有任何重采样或滤波。muxed 中间态（`ch0,ch1,…,ch0,ch1,…` 逐字节轮转）正是 vendored 的 `scarletbook_process_frames()` 回调吐出来的形态，也是 `DST_FramDSTDecode()` 的输出形态——**DSD 与 DST 只在「怎么拿到 muxed」这一步分叉，往后完全同构**（D-037 的落地形态）。muxed 的一个 `声道数 × 4096` 字节窗口恰好对应 DSF 的一个超块，所以随机读只需定位到超块、必要时从轨首重解追上来。声道顺序实测核对：6 声道区取 20 秒做逐声道 RMS，得 L −20.5 / R −20.8 / C −26.0 / LFE −30.2 / Ls −26.0 / Rs −26.0 dB——前置对near-equal、环绕对near-equal、LFE 最低，是标准 5.1 的形态，说明解交织与声道次序正确。
- **D-040 helper 的 stdout 有一道保险闸，且带可复现自检。** `main()` 第一件事是 `dup(1)` 出一个私有 fd 给协议独占，再 `dup2(2, 1)` 把 `stdout` 整个指向 stderr；Windows 侧另加 `_setmode(_O_BINARY)`（文本模式会把 0x0A 翻成 0x0D 0x0A，而 DSD 数据里这种字节遍地都是，铁律 #5）。此后 vendored 代码里任何 `printf` / `fprintf(stdout)` / `fputs(stdout)` / 甚至 `write(1, …)` 都只会落到 stderr，撕不到帧流。`MD_SACD_STDOUT_TEST=1` 会让 helper 在启动时故意用这四种方式各写一行，用来实测这道闸——**这条路径存在的意义是让「库函数误写 stdout」有可复现的证据，而不是靠口头保证**（D-034 排除 EuFlo 分支正是因为它把诊断改到了 stdout）。
