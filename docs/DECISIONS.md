# 决策记录（DECISIONS）

规则：影响架构、依赖、协议、验收口径的决策都记一条；一行现状 + 一行理由。修改既有决策 = 新增条目并标注取代关系，不改历史。

- **D-001 播放内核 = libmpv。** ffmpeg 生态 + gpu-next 渲染，seek/截图/HDR/独占输出全覆盖；PotPlayer 闭源不可用，自研解码链违反铁律 #1。
- **D-002 菜单策略 = 虚拟菜单优先，BD-J 列 P3 评估。** 演唱会碟菜单本质是选曲；MusicDisc 数据可做出优于原生菜单的体验。开源 BD-J 仅 libbluray+JVM 一条路，兼容性天花板即 VLC/Kodi，不值得阻塞主线。
- **D-003 明确不做解密。** 只支持已解密资源，绕开 AACS/CSS 的法律与工程复杂度；加密盘给明确报错。
- **D-004 License = GPL-2.0-or-later。** 依赖链（mpv 默认构建、libdvdread、scarletbook 血统代码）均为 GPL 系；项目本身定位社区工具，开源为正资产。
- **D-005 UI = Qt 6 Quick，渲染强制 OpenGL RHI。** mpv render API 需要 GL；Metal 默认路径不可用（CLAUDE.md 深坑 #1）。
- **D-006 SACD 解码隔离在独立 helper 进程。** GPL vendored 代码物理隔离、崩溃隔离、协议清晰（ARCHITECTURE §SACD）。
- **D-007 开发与 M1 验收平台 = macOS；Windows 走 T8 构建通道、M2 打包首发。** 开发机为 macOS；Qt+libmpv 栈双平台同源。
- **D-008 碟片指纹 v1 规范冻结。** 见 ARCHITECTURE §指纹；发布后不可变，演进走 v2 双写。
- **D-009 libmpv = 自编译到 `third_party/prefix`（取代系统 Homebrew 版）。** Homebrew 的 mpv 0.41.0 编入了 libbluray（`bd://` [OK]）但**未编入 dvdnav**（`dvd://` 缺失），而 M1 T4 必须走 `dvd://<title>`，故按 CLAUDE.md 深坑 #3 用 meson 自编译，`-Dlibbluray=enabled -Ddvdnav=enabled`，探测结果转为 `bd://` 与 `dvd://` 双 [OK]。CMakeLists 已实现 prefix 优先于系统的 pkg-config/CMake 查找；重建脚本见 `scripts/build-deps.sh`。**交叉验证**：GitHub Actions macos-14 干净 runner 上（run 32915478493）同一脚本独立复现出 `bd://` [OK] / `dvd://` 缺失，确认这是 Homebrew mpv 的构建口径而非本机环境问题。
- **D-010 T0 骨架不打成 macOS .app bundle。** M1-PLAN T0 验收口径是 `./build/md-player` 直接出窗口，故 `MACOSX_BUNDLE FALSE` + 产物落 build 根；正式打包形态放 M2（Windows 首发打包一并处理）。
- **D-011 DVD 栈（libdvdread + libdvdnav）一并自编译，且 `-Dlibdvdcss=disabled`。** Homebrew 的 libdvdread 把 **libdvdcss 编成硬加载项**（`LC_LOAD_DYLIB`，非 dlopen），libdvdnav 依赖它，链条 libmpv → libdvdnav → libdvdread → libdvdcss 会让解密库随进程启动被加载，直接违反铁律 #2。故在 prefix 内重建两库并关闭该选项；递归依赖闭包扫描 46 个库，确认无 libdvdcss / libaacs / libbdplus。**残留说明**：关闭链接后 libdvdread 上游仍保留运行时 `dlopen("libdvdcss.2.dylib")` 兜底分支，我们既不链接也不分发该库，用户自行安装属其自身行为；如需彻底铲除需 patch 上游源码，见【待决策】。
- **D-012 libdvdcss 立场固化：不链接、不携带、不 patch 上游。** 取代 D-011 的【残留说明】部分（D-011 其余内容仍有效）。三条约束：(1) 自编译 libdvdread 一律 `-Dlibdvdcss=disabled`，任何平台的分发包都**不携带** libdvdcss；(2) **不对上游源码做任何 patch**，其运行时 `dlopen` 兜底分支原样保留，维护成本为零；(3) 用户自行安装 libdvdcss 属其自身行为，**加密盘行为的确定性由应用层保证**——DVD 模块自检扰码位并主动拦截，不依赖底层库是否恰好解不开。验收口径见 M1-PLAN T4。

- **D-013 demuxer 缓存维持 `demuxer-max-bytes=768MiB` / `demuxer-max-back-bytes=512MiB`，不为 UHD 上调。** T2 在 83.2 Mbps 的 4K HEVC 原盘流上实测：拖动中位到位 41ms、19 次采样 18 次 <100ms，手感与 42.9 Mbps 1080p 样本（中位 43ms）基本一致，**大缓存 + keyframes seek 的配方在 UHD 码率下依然成立**，没有上调的必要性。已知代价：83 Mbps 下 512MiB 回退窗口仅覆盖约 **49 秒**，超出该窗口的大幅**向后**拖动会退化为落盘重读，实测偶发 ~200ms 级延迟（T2 中出现 1/19 次，222ms）。此现象**定性为已知特性**，不作为缺陷。**约束：今后任何缓存参数改动，必须重跑 T2 的 seek 基准并与本条记录的数字对比后方可提交**（拖动节流违反次数、到位耗时最小/中位/最大、<100ms 占比）。
- **D-014 蓝光标题列表 = `TITLES_RELEVANT` 且不做时长过滤，按 libbluray 枚举顺序展示，主标题只加徽标不重排。** `TITLES_RELEVANT`（= 去重复标题 + 去重复 clip）能滤掉混淆用 playlist，但**不能**再叠加最短时长过滤：演唱会碟常把曲目组拆成多条短 playlist，滤掉就等于丢内容（ARCHITECTURE §bluray「始终同时展示完整列表」）。代价是 UHD 原盘的一堆 5 秒占位 playlist 也会列出来（THE WARNING 那张 11 条里有 5 条是 5 秒），用主标题徽标 + 打开即播主标题来抵消。**不按时长排序**：那会打乱演唱会碟的曲目顺序，比列出几条占位项更糟。
- **D-015 libbluray 的 1.5 新能力必须「编译期宏 + `bd_get_version()` 运行时版本」双重把关。** 章节名（`BLURAY_TITLE_CHAPTER::chapter_name`）与 HDR 元数据（`BLURAY_STREAM_INFO::dynamic_range_type`）都是**结构体成员**而非函数，无法用 dlsym 探测；对着 1.5 头文件编译却链接到 1.4 运行库时读它们会越过实际分配的内存。故 `BlurayDisc.cpp` 两道关同时卡，任一不满足即降级（章节名→「第 N 章」，HDR→不显示）。**实测**：REJOICE_BONUS 与 THE WARNING 两张样本碟内均无 META TOC，章节名 0 条，走的正是降级路径。
- **D-016 加密判定排在 `bluray_detected` 之前。** 加密盘的 `index.bdmv` 本身不加密、通常能解析，但一旦某张盘结构解析失败，先报「不是蓝光」会把用户引向完全错误的方向。故 `aacs_detected && !aacs_handled`（BD+ 同理）一命中就立刻返回 Encrypted。验证手段见 `tests/fixtures/make_bd_skeleton.py --aacs`——自造骨架即可让 libbluray 报 `aacs_detected=1 / aacs_handled=0`，不需要真加密盘。
- **D-017 碟类资源的断点键 = `<碟根>#<URI>`，不是 URI 本身。** `bd://mpls/1` 在任何一张碟上都长一样，直接拿它做 ResumeStore 的键会让不同碟共用同一条断点记录，续播跳到毫不相干的位置。普通文件仍以路径为键，行为不变。
- **D-018 覆盖在播放画面上的面板一律 `focus: false`，键盘关闭改用窗口级 `Shortcut`。** Qt Quick 的 Popup 一旦拿到 activeFocus，`QQuickPopupItem` 就会成为窗口的 `activeFocusItem`，此后窗口级 `Shortcut` 即便 `enabled === true` 也**永不触发**——T3 的标题面板一开，空格 / 方向键 / 截图快捷键全哑（实测 `activeFocusItem=QQuickPopupItem("TitlePanel")`，改 `focus: false` 后回到 `QQuickRootItem("Main")`，快捷键立即恢复）。代价是 `Popup.CloseOnEscape` 随焦点一起失效，Esc 关闭改由窗口级 Shortcut 承担（正因为焦点没被抢走，它才触发得了）。**播放器的键盘手感优先于面板的焦点导航**，后续任何叠加面板都按此办理。同一机制也是 issue #1（续播框回车失效）的根因线索。
- **D-019 标题列表加「隐藏 10 秒以下条目」开关，默认开启，只隐藏不删除。** D-014 定的「不做时长过滤」保证了数据层的完整性，但展示层需要一个出口：UHD 原盘的占位 playlist（THE WARNING 那张 11 条里 5 条是 5 秒）混在列表里纯属噪音。故过滤只发生在展示层——`BlurayController::playlists` 始终是碟内**完整**结构（Studio 模式将来要按完整结构做曲目编排），面板读的是过滤后的 `visiblePlaylists`，每个条目自带碟内原始下标 `index`，播放与高亮一律按原始下标走。**两条永不隐藏**：主标题、以及当前正在播放的那条（否则会出现「在播的标题不在列表里」的怪状态）。阈值 10 秒硬编码在 `kShortTitleSeconds`，开关状态存 `QSettings("ui/hideShortTitles")`，默认 true。
- **D-020 打开碟不自动弹标题面板，改为播主标题 + 每次会话一次的上手提示。** 面板是左侧抽屉，宽度约占窗口 1/3，自动弹出会立刻遮住刚开始播的画面，而「打开碟就是想看主标题」才是绝大多数场景。故打开碟只做两件事：播主标题、弹「已载入蓝光碟：X（N 条标题）」提示条。面板入口保留两个常驻通道：播控条的 ☰ 按钮（碟类资源才出现）与快捷键 `T`。**上手提示按会话计**：每次启动后打开的**第一张**碟，在碟名提示淡出后补一条「按 T 选择标题 / 章节」，同一次运行内不再重复。状态是进程内的一个静态标志，**不落盘**——曾用 `QSettings("ui/titleHintShown")` 做成「装了之后永远只提示一次」，但这条提示的作用是唤醒记忆而不是教学，隔几周再打开时用户同样需要它；按会话计既保证同一次使用里零重复打扰，又不至于让人永久失去线索。面板入口（☰ 与 `T`）本就常驻，提示只是补充。
- **D-021 DVD 播放定位符 = `dvd://<titleNumber-1>`，即 mpv 侧 0 起编号。** libdvdread 的 title 是 1 起（`tt_srpt` 顺序），mpv 的 `dvd://N` 是 0 起，换算在 `PlayerController::loadDvd` 一处完成。**实测确认**：`dvd://2` 落在 libdvdread 的 title 3 上，且与 `--edition=2` 完全等价——mpv 的 dvdnav 把整张碟当作一个文件、把各 title 暴露为 edition，`dvd://N` 只是开场即切到第 N+1 个 title 的语法糖。七条 title 的时长与 libdvdread 解出的值逐条吻合（02:00:49 / 14.0 / 108.0 / 5.667 / 21.0 / 30.5 / 21.0 秒）。
- **D-022 DVD 加密拦截 = 应用层读 VOB 扇区自检 PES 扰码位，且判定排在结构解析结论之前。** 落实 D-012「加密盘行为的确定性由应用层保证」。位置**已实测确认**为 M1-PLAN 所给的参考位置：DVD 的 pack 头恒为 14 字节无填充，紧随其后的 PES 头 flags 字节落在扇区偏移 `0x14`，其 bit5..4 即 `PES_scrambling_control`。每个 title set 采样 32 个扇区、最多探 4 个 title set，只统计 pack 头开头且 stream id 为 `0xBD` 或 `0xC0..0xEF` 的扇区（导航包 `0xBB/0xBF` 不带该字节）。**实测**：三张已解密真盘 8 个 title set 共 100+ 个 PES 扇区全部为 0；自造加扰骨架 32/32 命中并给出统一文案。顺序上与蓝光侧 D-016 同口径——先判加密，再判「结构读不了」，否则加密盘会被误报成损坏盘。**本函数只读原始扇区看两个比特，不做任何解密。**
- **D-023 DVD 的音轨 / 字幕按 PGC 的 `audio_control` / `subp_control` 可用位过滤，面板摘要不显示声道数。** `vtsi_mat->nr_of_vts_audio_streams` 是该 title set 的**上限**而非某条 title 实有的流数：张学友那张碟声明 8 音轨 / 32 字幕，mpv 实际只有 4 音轨 / 0 字幕，多出来的条目 attr 里全是垃圾值。真实可用性写在 PGC 的 `audio_control[i] & 0x8000` 与 `subp_control[i] & 0x80000000` 上，按它过滤后与 mpv 逐条对齐。另：`audio_attr.channels` 本身也不可靠（同一张碟的 DTS 轨 IFO 写 5 声道、实际码流 6 声道），故面板摘要只列编解码器，声道数以播控条上由 mpv 提供的音轨列表为准——与蓝光侧口径一致。
- **D-024 碟片指纹 v1 的字节拼法就此钉死。** ARCHITECTURE 只写了拼接的成分，具体编码必须落到字节才可复现，故在此固定，改动等于换指纹（只能新增 v2 并双写）。**蓝光**：`index.bdmv` 全文 ∥ `MovieObject.bdmv` 全文（缺失按空串参与，纯 BD-J 碟见过缺的）∥ 按文件名升序的每个 `BDMV/PLAYLIST/*.mpls` 的（文件名 UTF-8 字节 ∥ 文件大小的十进制 ASCII ∥ 该文件全文的 sha256 **32 字节裸值**），三段之间不插分隔符。文件经 `bd_read_file` / `bd_open_dir` 读取，**目录与 ISO 走同一条路径**。**DVD**：`VIDEO_TS.IFO` 全文 ∥ 按 title set 编号升序的每个 `VTS_xx_0.IFO` 的 sha256 裸值；title set 数取自解析后的 VMG（`vmg_nr_of_title_sets`），不去猜 1..99。**SACD**：LSN 510 起 10 个扇区（scarletbook 的 `START_OF_MASTER_TOC` / `MASTER_TOC_LEN`）的原始字节——SACDText 区块本就在这 10 个扇区内，整块参与即可，不必把 scarletbook 结构体提前拉进 M1。输出为小写十六进制。**实测**：同一张 DVD 放在四个不同路径（原目录、直接拖 VIDEO_TS、套 2 层、套 3 层）下算出的指纹完全相同（`1ceef8a3…`），六张碟两两不同。M1 只落日志，**不做任何网络上行**。
- **D-025 碟根下探：深度上限 3 层，命中即停，多候选一律报错。** 从拖入目录算起，碟根最深可在第 3 层被找到（实测：第 2、3 层能找到，第 4 层找不到）。命中 `BDMV/index.bdmv` 或 `VIDEO_TS/VIDEO_TS.IFO` 的目录、以及 `.iso` / `.img` 文件都算候选；判定看的是**结构文件**而非目录名——只有空 `VIDEO_TS` 目录的残缺资源相当常见，那不该被收下再在打开时报错。递归遇到 `BDMV` / `VIDEO_TS` / `CERTIFICATE` / `AUDIO_TS` 即停止下钻，不进碟内扫描（UHD 原盘上很慢且没有意义）。**恰好一个候选就直接打开；两个及以上一律报错让用户指定，绝不替他挑一张。** 提示条只列碟名不列相对路径——王菲那套四碟的相对路径每条一百多字符，拼出来比窗口还宽，反而认不出哪张是哪张。
- **D-026 镜像完整性只比对「结构声明的总大小」与「文件实际大小」，不抽扇区试读。** 试读失败在真盘上会误伤（划痕、慢速光驱、网络挂载），而截断镜像的特征恰恰是「头部结构完好、尾部内容缺失」，用声明值一比即知。两条路线：有 ISO9660 主卷描述符（DVD / SACD 镜像）就比 `volume space size × logical block size`；纯 UDF 镜像（蓝光原盘常见，无 ISO9660 桥）则看 UDF 规定的「LSN 256 与卷末各有一个锚点描述符」——头部锚点在、卷末锚点不在即为截断。两者都不成立时**不下结论**，交给后面的模块判，别在这里冒充「截断」。**实测**：六张真镜像（DVD×2、BD×3、SACD×1）全部判为完整，各截到 8MiB 后全部当场拦下；自造的两个骨架（`make_broken_iso.py`）覆盖两条路线，不含任何版权内容。判定发生在**打开阶段**，不会先列出标题再在播放时失败。
- **D-027 SACD 在 M1 只识别不播放，且不落到 mpv 的英文原文。** 按 ARCHITECTURE 判定表，`.iso` 先查 `510*2048` 处的 `SACDMTOC` 签名，命中即判为 SACD，给「识别到 SACD 碟，播放支持将在后续版本提供」并把指纹写进日志。此前 SACD ISO 会一路落到普通播放、由 mpv 报一句英文 `unrecognized file format`——识别得出却说不清楚，比不认识更糟。播放实现归 T6。
- **D-028 截断判定改用文件系统级声明，取代 M1-PLAN T5 括号里建议的「DVD 看 VOB last sector、蓝光看 m2ts clip 长度」。** 补充 D-026 的选型理由。括号建议要走应用层结构解析：DVD 得逐个 IFO 解 `vts_ptt_srpt` / cell playback 表求出最末 VOB 扇区，蓝光得逐条 mpls 解 clip 的 SPN 区间再回查 clpi——两条路都得**先把碟解析成功**才谈得上校验，而截断镜像恰恰可能在解析阶段就崩在半路（T4 实测的 8MiB 截断件 IFO 还读得出来，是运气不是规律），且这套解析对 UHD 原盘慢得离谱。文件系统层的声明值（ISO9660 主卷描述符的 `volume space size × logical block size`；纯 UDF 镜像的卷末锚点）位置固定、读两三个扇区就有结论、且**先于**任何碟结构解析，正好卡在「打开阶段就判死」这个验收要求上。两种口径的目标一致（都是问「文件尾巴还在不在」），文件系统层是更浅也更早的那一层，故取代之。
- **D-029 D-026 的已知误伤面 = 非规范 UDF 镜像，收窄逻辑三重。** UDF 规范要求卷末（或倒数第 256 扇区）必有锚点描述符，但这是**规范约定**，个别刻录/转储工具产出的镜像可能不满足，此时完整镜像会被误判为截断。收窄做法：(1) 只在**头部锚点存在**（LSN 256 命中）时才允许下「截断」结论——连头部锚点都没有说明这根本不是 UDF 镜像，不归本判定管；(2) 卷末与倒数第 256 扇区**任一命中即放行**，覆盖规范允许的两种摆放；(3) ISO9660 与 UDF 两条路线都不成立时**不下结论**，交给后面的模块判，不冒充「截断」。实测六张真镜像（DVD×2 / BD×3 / SACD×1）零误伤。若日后出现误伤实例，处置方向是加一条「用户强制打开」的逃生口，**不是**放宽判定——放宽等于把 T4 那个「先列标题、播放时才失败」的缺口重新打开。

- **D-041 DST 与多声道的验收素材已到位，阶段 0 的挂账取消。** 阶段 0 盘点时手头 4 张 SACD 全是纯 DSD（3-in-14）且无多声道区，DST 与多声道两条验收本已列为「素材缺失、挂起」。控制器随后指出 `Sarah Brightman (3SACD)`，实测三张碟的 2ch 区与多声道区**全部是 DST 编码**，多声道区均为 6 声道。至此 T6 的四类组合（DSD/DST × 2ch/多声道）里有三类有真碟可验，唯一没有的是「多声道 + 纯 DSD」——这个组合在实物碟上本就罕见（多声道区几乎必用 DST 压缩），不再挂账。
- **D-042 SACD 接入形态：`sacd://<token>/<area>/<track>` + 每条流一个 helper 子进程。** mpv 的 `stream_cb` 回调跑在**解复用线程**上，不是 GUI 线程，所以 `SacdStream` 里刻意不碰任何 QObject：每条流用 `posix_spawn` 起自己的 helper、走裸管道说话，生命周期与流一致。URI 里放 token 而不是路径——路径要穿过 mpv 的 URL 解析、我们的字符串拼接、helper 的 JSON 转义三道关，token 一个整数省掉全部转义风险，映射表留在进程内。**崩溃隔离因此是天然的**：实测播放中 `kill -9` helper，播放器不崩、UI 照常响应。但 mpv 在流读失败后只是静默停住、不发 end-file，用户看不到任何解释，故加了一个原子旗标 + GUI 侧每秒轮询，把它翻成一条明确文案（`kSacdHelperLost`）。
- **D-043 DST / DSD 的随机 seek = 帧→LSN 增量索引（方案 A），不落磁盘缓存。** 每个 SACD 帧解出来恰好是 `声道数 × 4704` 字节，且帧头自带绝对时间码，于是「帧号 ↔ DSF 字节区间」是纯算术，索引只需存「帧号 → 起始扇区」。构建是**增量**的：要哪一帧就往后扫到哪一帧，**只解析扇区头 / 包头 / 帧信息那几十个字节，不碰负载、不解码**；已扫过的部分不重扫，全程不做全量预扫。一个 DSF 超块（每声道 4096 字节）最多跨两帧，所以定位后只需解一到两帧。**纯 DSD 复用同一条路径**——它的「解码」只是拷贝，索引照建，代码没有第二条分支（D-037 的同构口径贯彻到 seek 层）。**实测**（M2 Mac，本会话冷轨）：已索引区间回退 seek 中位 **5–7 ms**（DST 2ch / 6ch），纯 DSD **0 ms**，均远低于 D-013 定的 T2 口径 100 ms；未索引区间一跳到轨尾（含索引追赶）**8–25 ms**。改造前同样的回退 seek 要重解整轨，6 声道最坏 **27 秒**。放弃磁盘缓存方案的理由：一条 6ch 轨要 400 MB，还要定缓存位置与清理策略，而索引法把成本压到了几毫秒，没必要。
- **D-044 SACD 专辑名降级链 = 碟内 SACDText → ISO9660 卷标 → 文件名去扩展名。** 手头三张 Sarah Brightman 就是碟上**没有 master text** 的实例（`text_area_count=0`），不给降级面板标题会是空白。指纹日志的 `label` 同链——T5 遗留 5（label 是卷标而非专辑名）就此关闭：王菲《天空》现在落的是 `label":"Tian Kong"`，Sarah Brightman 落的是文件名。**`sha256` 不受影响**，它哈的始终是 LSN 510 起 10 个扇区的原始字节（D-024 / D-036）。
- **D-045 曲目无缝切换必须走 mpv 播放列表，且 append 要等 `MPV_EVENT_FILE_LOADED`。** `gapless-audio=yes`（baseline.conf）只对**播放列表内的条目切换**生效；每首都用 `loadfile … replace` 的话它就是摆设。故选中一曲时把同一区后续曲目全部 `loadfile … append` 排进去。**踩到的坑**：`loadfile replace` 是异步的，紧接着 append 会被它连锅端掉——实测 `playlist-count` 只剩 9（该是 10），末曲于是变成「最后一项」，`keep-open=yes` 让播放停在曲末不再前进，看起来就像 gapless 没生效。改为在 `fileLoaded` 事件里才 flush 队列，`playlist-count=10`，边界处日志出现 `SACD 无缝换轨: playlist-pos=1 → 第 2 曲 Qi Zi`。跨区不排队（多声道区本就不可播）。
- **D-046 SACD 的 +6dB 增益用 lavfi 的 volume 滤镜挂在 `af` 上，且只在放 SACD 时挂。** DSF 经 ffmpeg 解为 PCM 后比 foobar2000 + SACD 插件低约 6dB（CLAUDE.md 深坑 #5）。实现是 `af add @sacdgain:lavfi=[volume=6dB]`，换回蓝光 / DVD / 普通文件时 `af remove @sacdgain`——**不能用全局音量或 replaygain-fallback**，那会给普通片源也平白加 6dB。默认开；临时开关是快捷键 `G` + toast 回显（`kSacdGainOn` / `kSacdGainOff`），**正式入口在 T7 设置页**，这条快捷键是为了让「开/关 A/B 是否可闻」这项人工验收跑得起来。
- **D-047 SACD 的 +6dB 增益后面必须跟限幅器，否则输出削顶。取代 D-046 的滤镜串写法。** 阶段 2 人工验收报「seek 到目标位置后先出杂音」，根因**不在 seek**：数据链路四层验证全部干净（helper 随机存取 vs 顺序参照件逐字节相等；mpv 经 stream_cb 实收的 1 909 次读、含 19 次真流 seek，与参照件逐字节相等；ffmpeg 对离线参照件做输入 seek 与从头解码相同率 100.0%；拖动进度条实测每次 seek 0–13 ms）。真凶是**增益越界**：这张碟的 DSD 母带在 ffmpeg 口径下峰值已到 **−3.6 dBFS**，再加 6dB 冲到 **+2.44 dBFS**；实测播放器真实输出（`ao=pcm` 录下整段）峰值 **+3.51 dBFS、160 578 个样本越界（0.046%）**，音频设备只能硬削，听感就是响处一片杂音、安静处又恢复正常——与报告的现象完全吻合。**改法**：`af` 由 `lavfi=[volume=6dB]` 改为 `lavfi=[volume=6dB,alimiter=limit=0.977:level=disabled,aformat=sample_fmts=fltp]`。限幅器把峰值压到 −0.2 dBFS，只动那 0.046% 的峰值样本；末尾的 `aformat` 是必需的——不加它 mpv 会把整条链路谈判成 s16，白白丢掉浮点精度（实测：加之前录出来是 `pcm_s16le`，加之后是 `pcm_f32le`）。**修复后实测播放器输出峰值 −0.2 dBFS、零越界。** 「+6dB 是否该配限幅」属听感取舍，已列入待决策；但**硬削是缺陷，不是取舍**。
- **D-048 SACD 自 T6 阶段 2 起为真播放，取代 D-027。** D-027（「M1 只识别不播放，给『播放支持将在后续版本提供』」）是 T5 期间的临时口径，随阶段 2 落地失效：`Kind::Sacd` 现在直接调 `SacdController::openPath` 播放，文案常量 `kSacdNotSupportedYet` 已从 `strings.h` 删除。**不改历史**，D-027 原文保留在册，取代关系记在这里。同时核过下游文档：`docs/ARCHITECTURE.md §SACD` 与 `README.md` 已随阶段 2 更新（多声道置灰、无缝换轨、帧索引 seek），**无与现行为相反的残留**；`docs/M1-PLAN.md` 的 T5 条目仍写着「SACD ISO 在本任务只做识别」——那是 T5 任务本身的定义与验收口径，属历史记录，不作修改，以本条为准。
- **D-049 SACD 专辑名降级链改为「碟内 master text → ISO9660 卷标 →『未命名 SACD』」，取代 D-044 的末级。** D-044 的末级是「文件名去扩展名」，实测在三张 Sarah Brightman 上显示成 `Sarah Brightman - Eden`——那是下载者起的文件名，摆在碟名位置上会被当成碟内元数据，是**冒充**。改为显式的「未命名 SACD」：信息量更少，但诚实。卷标由指纹层顺带读出（`computeSacd` 本来就要解 ISO9660 主卷描述符），所以路由层先算指纹、再把 `fp.label` 作为兜底传给 `SacdController::openPath`；碟内有 master text 时反过来用它覆盖指纹日志的 `label`。指纹 `sha256` 一如既往不受任何显示层变化影响。
- **D-050 面板是 Popup，盖不住它只能靠它自己让位；播控条在面板打开时常驻。** Qt Quick 的 Popup 渲染在 overlay 层，普通 Item **无论 z 多大都盖不过它**——想让播控条露出来，只有让 `TitlePanel` 自己把高度减掉播控条那一截（新增 `bottomReserve` 属性）。同时面板打开时停掉 2.5 秒自动隐藏计时器：既然给它让了地方，那块地方就不该是空的。人工验收里「不知道在哪里切换声道与字幕」的直接原因就是全高抽屉把 ☰ / 播放 / 时间 / 音量 / 音轨字幕入口整排压在下面。**实测**：面板打开状态下，在 x=172（远在抽屉 420px 宽度之内）点播控条的「下一个」按钮，曲目从 1 换到 2 —— 播控条确实完整可用。
- **D-051 issue #3（音轨/字幕入口不可发现）按 A+D+不遮挡三件套关闭。** (A) 两个下拉框收起时显示 `音轨：xxx` / `字幕：xxx` 前缀——此前两个框长得一模一样，用户没有任何线索知道哪个是哪个；前缀只改 `displayText`，展开后的列表项保持原样。(D) 碟上有字幕、当前却关着时，载入后隔 3.6 秒提示一次「这张碟有 N 条字幕，在播控条的『字幕』下拉框里选」，每张碟只提一次（挂在 `tracksChanged` 上，因为轨道表要等 mpv 载入完才有）。(不遮挡) 见 D-050。原计划把 issue #3 排到 T7，人工验收证明它已经在挡路，故提前做掉。
- **D-052 上一个 / 下一个条目 = 面板模型里的相邻可播条目，不走 mpv 的 playlist-prev。** SACD 是上/下一曲、蓝光与 DVD 是上/下一个标题，语义对齐，跳过不可播条目（SACD 多声道区），到头即停不循环。入口：播控条的 ⏮ / ⏭ 按钮 + `PgUp` / `PgDown`（另兼容 mpv 老习惯的 `<` / `>`）。**没有**按原设想「把同区全部曲目排进 mpv 播放列表」来让 `playlist-prev` 可用：那要么得先载入区首曲再跳，播放会短暂错位；要么得重排整个列表。改用 `playIndex(currentIndex ± 1)` 直接重载，代价是**往回跳时有一次正常的载入间隙**（往前连播仍然是 gapless，因为 D-045 的队列没动）。手动操作有间隙可以接受，自动连播无缝才是要害。
- **D-053 SACD 的滤镜串必须以 `aresample=88200` 打头；杂音的真凶是「把 352.8 kHz 直接递给音频设备」。取代 D-047 对根因的判断（限幅本身保留）。** D-047 认定的「+6dB 削顶」是**实测存在的缺陷**（整轨 160 578 个样本越界，占 0.046%，已由限幅器修掉），但人工复验推翻了它是杂音根因——限幅之后杂音仍在，且**暂停/恢复瞬间也有**，而暂停恢复不读盘、不 seek、不解码，杂音不可能来自 helper 或数据路径。重新分离后定位到 AO 层：
  - `MD_LOG_MPV=v` 抓到 mpv 的协商结果是 `AO: [coreaudio] 352800Hz stereo 2ch floatp`，而 CoreAudio 实测（`kAudioDevicePropertyAvailableNominalSampleRates`）本机内置扬声器**只支持 44100 / 48000 / 88200 / 96000**，当时运行在 48000。设备端只能自己做 7.35 倍降采样，那层抗混叠滤波不由我们控制。
  - DSD 解出来的 352.8 kHz 流里带着 DSD 固有的超声整形噪声，实测 30 kHz 以上 **mean −24.3 dB / peak −9.7 dB**（AO 入口处）。这些能量被设备端的转换整片折回可听带，听感就是「沙」。
  - **每次 AO 重启都会重新起这个转换器**——`starting audio playback` 在暂停/恢复、seek、换轨时各出现一次，与三种症状的时刻一一对应。
  - 改法：在 SACD 专属的 `@sacdgain` 串最前面加 `aresample=88200`，用 swresample 的正经抗混叠滤波先把带宽收掉。88200 是本机设备原生支持的速率，也是 352800 的整数分频；即便别的机器不支持，此时信号已带限，CoreAudio 再转一次也不会有混叠。**顺序还必须是「先重采样、再增益、再限幅」**：否则增益作用在带超声噪声的信号上，限幅器也会被超声峰值牵着走，对可听内容做出莫名其妙的增益起伏。
  - **客观对照**（同一张碟、同一操作序列、`ao=pcm` 录 AO 入口）：AO 采样率 352800 → **88200**；30 kHz 以上 mean **−24.3 → −59.6 dB**、peak **−9.7 → −42.8 dB**（各降 33–35 dB）；逐声道相邻样本差中位 **0.399 → 0.055**；全带 mean −17.1 → −17.9 dB、peak −0.2 → −0.3 dB（可听内容与限幅上限基本不变）。
- **D-054 「seek 后过几秒才出声」= mpv 对未缓存的前向 seek 采取顺序读而非流 seek，撞上 DST 单线程解码速度。已定位，本轮未修。** 实测（默认 baseline.conf，2 声道 DST，播到 5 秒时缓存覆盖 0–102 秒）：点进度条跳到 163.6 秒，mpv 的 lavf 层 `execute seek` → `seek done` 耗时 **2.96 秒**，而 `MD_SACD_DUMP` 显示这段时间里**一次流 seek 都没有**——mpv 是顺序往前读、把缓存从 102 秒铺到 163 秒，按 DST 单线程 14 MB/s 正好 2.9 秒。**两个候选杠杆都试过且都无效**：`demuxer-readahead-secs` 压到 5 秒，耗时 2.96 → 2.96 秒（无变化）；再加 `demuxer-max-bytes=32MiB` / `back=16MiB`，三次远跳分别是 5.2 秒 / 瞬时 / 25 毫秒（不稳定，且第一次更差）。**没有把无效改动留在树上。** 后续两个方向：(a) DST 多线程解码（D-033 偏离点 1 把它列为 P2），把追赶速度提上去，2ch 4 线程约能到 80× 实时；(b) 找到让 mpv 对纯音频流走真流 seek 的正确开关——真流 seek 那条路实测只要 0–13 毫秒（小缓存配置下 19 次全部命中）。**注意这与「拖动」无关**：一次完整拖动实测发出 29 次 seek（28 keyframes + 1 exact），到位耗时最小 0 / 中位 0 / 最大 14 毫秒，真流 seek 0 次——落在缓存里的拖动是流畅的，深坑 #2 的配方不需要为纯音频另立口径。
- **D-055 拖动进度条时，纯音频资源不发 seek；深坑 #2 的配方仅对有画面的资源成立。这是纯音频通病、自 T2 接入进度条起就潜伏至今，不是 SACD 专属——普通 flac / mp3 / m4a 同样中招，只是此前没有人拖过它们。** 深坑 #2「拖动中 ~30Hz 发 keyframes seek」的**全部理由是即时出画面**。纯音频没有画面，理由不成立而代价全在：实测一次 3.5 秒连续拖动发出 **88 次 seek**，在**真实 CoreAudio 输出**下换来 **89 次 `starting audio playback`**——约每秒 30 次 AO 重启，每次只放约 4 毫秒碎片，听感就是拖动全程一片杂音。改法：`onSeekDragged` 只在 `Player.hasVideo` 时才发 `seekDrag`；纯音频拖动中只更新进度条与时间标签，松手时照旧发一次 `absolute+exact`。**有视频轨的资源一个字未动**，D-013 的 T2 基准口径不受影响。
  - **`hasVideo` 的两个坑**：(1) 纯音频资源上 mpv 的 `dwidth` 发的是 `MPV_FORMAT_NONE` + 空指针，会被 `handlePropertyChange` 的空指针闸门吞掉（深坑 #10），故该判定必须提到闸门之前；(2) **内嵌封面也会被 mpv 报成视频轨并给出 dwidth**——带封面的 flac 因此被误判成「有画面」，拖动又走回连拍那条路，需再查 `current-tracks/video/albumart` 排除。
  - **修前/修后客观对照**（同一操作、同一方法、真实 AO）：SACD 发出 seek **88 → 1**、`starting audio playback` **89 → 2**；带封面 flac **88 → 1** / **89 → 2**；mp4 保持 **39 次 seek**（视频路径未变）；蓝光保持 61 次发出 / 47 次入队。
  - **`ao=pcm` 录音在这个缺陷上是无效参照物，必须写明**：同一次拖动，`ao=pcm` 下只有 **2** 次 `starting audio playback`（真实 AO 下是 89 次）——录音法把要测的那件事本身消掉了，录出来 4070 个 50ms 窗零超阈，什么也证明不了。上一轮 E3 用「每次 seek 到位 0–14 ms」论证「拖动没问题」，同样是参照物选错（延迟不等于噪声）。两处都并入 CLAUDE.md 深坑 #11。
  - **判定字段与全类型实测**（3 秒拖动，音频侧期望 1 次、视频侧期望 ~30 次）：判定用 mpv 的 `dwidth`（>0 即有画面），再用 `current-tracks/video/albumart` 排除内嵌/外挂封面。实测——flac 带封面 **1**、flac 无封面 **1**、flac 真无封面（干净目录）**1**、mp3 带封面 **1**、m4a 带封面 **1**、SACD **1**；mkv **35–46**、mp4 **42**、只有视频轨无音频 **32**、蓝光 **47**、DVD **48/57/61**。DVD 曾测到一次 23，为鼠标事件投递的测量方差，用改动前的 ControlBar 跑同一脚本得 39/63/41，**有闸门不低于无闸门，非回归**。
  - 滤镜链的贡献：整场拖动中 `Setting option 'graph'` 只出现 **1** 次，即 `@sacdgain`（含 alimiter）**不随每次重启重建**，限幅器的前瞻/attack 状态不是本缺陷的来源。
- **D-056 「前向 seek 到未缓存区间要等几秒」是 mpv 解复用器的既定行为，方向 (b) 经实测关闭。** 补 D-054。`seek_fn` 打点后确认：mpv **确实会调**流层 seek（三次远跳共调 3 次），但只用于**向后**跳；**向前**跳到未缓存区间时它选择顺序读把缓存铺过去（实测 `#seek 134905948 -> 34586716` 说明第二次跳之前 mpv 已经把 134.9 MB 整轨读完）。接口侧没有问题：`seekable=yes`、`partially-seekable=no`、`demuxer-via-network=no`、`file-size=134905948` 与 helper `stat` 的 `dsf_size` 完全一致。**三个候选开关逐一实测无效**（同一操作，点进度条 85% → 25% → 60%）：基线 3282 ms、`cache=no` 3299 ms、`demuxer-seekable-cache=no` 3315 ms，而 `demuxer-max-bytes=16MiB` **更差**（6530 ms，缓存装不下于是反复重读）；三种配置下后两次（向后）跳都是 0 ms。结论：**没有 mpv 侧的开关能让它对前向 seek 走流 seek**，方向 (b) 关闭。剩下的只有方向 (a)——DST 多线程解码把追赶速度提上去（现列 P2，本轮按裁决不做）。
- **D-057 前向 seek 慢的定位收口：demuxer 快、流层正确，慢在「mpv 的前向读策略 × 我们的字节交付速度」两者相乘。** 补 D-056。分三层切开测：
  - **ffmpeg 的 dsf demuxer 不慢**。对本地参照 DSF（不经我们的 `stream_cb`）计时 `ffmpeg -ss 150 -i ref.dsf -t 1 -f null -`，三次均 **0.02 s**；同内容转出的 flac / wav 对照各三次均 **0.01 s**。同量级，`dsf_read_seek` 正常。（上一轮那个「输入 seek vs 从头解码相同率 100%」只测了**样本相同率**，没测耗时——同一个量测了两次却没测到点上，已并入 CLAUDE.md 深坑 #11。）
  - **我们的流层正确**：`seekable=yes`、`partially-seekable=no`、`demuxer-via-network=no`、`file-size` 与 helper `stat` 的 `dsf_size` 逐字节一致；`seek_fn` 打点证明 mpv **确实会调**它（向后跳时 0 ms 完成）。
  - **与「向前跳时 `seek_fn` 不被调用」如何自洽**：mpv 的解复用器缓存挡在 libavformat 之前。向前跳到未缓存区间时，mpv 选择**顺序读把缓存铺过去**而不是丢弃缓存重新定位，于是 demuxer 根本没机会调 `avio_seek`。纯 ffmpeg 没有这层缓存，所以本地文件测不出来。
  - **代价由字节交付速度决定**：DST 2ch 交付约 14 MB/s（单线程解码），铺 60 MB 就要 2.3–3.3 秒；**纯 DSD 同一操作连 `execute seek` 都没触发**（交付快到早已全轨缓存）。即：只有 DST 轨受影响，且时间 ≈ 待铺字节 ÷ 交付速度。
  - **候选方向与代价，不自行选**：(a) **DST 多线程解码**——现列 P2，2ch 四线程约 80× 实时，能把 3 秒压到 0.5 秒上下；改动局限在 helper 内，但要重新引入上游的调度层或自写线程池（D-033 偏离点 1 当初正是为了去掉它）。(b) **helper 改吐更易 seek 的容器/布局**——治不了本，mpv 慢是因为要**拿到字节**，换容器不会让 DST 解得更快；除非改成「预解码落盘」，那会动协议 v1 且要 400 MB 临时空间（D-043 已否决过）。(c) **接受现状 + UI 反馈**——加缓冲指示，把它降级为已知特性；零风险，但用户仍要等。

  - **收窄口径**：追赶**只发生在每首曲子载入后的铺缓存窗口内**（约 `时长 ÷ 20` 秒），且只对落在缓存前沿之后的目标；窗口过去、整轨进缓存之后，轨内任意 seek 立即完成（34–83 ms）。换轨会重新开一个窗口。按这个口径，M1-PLAN T6 验收原文的「允许首次追赶」**实际成立**（M1-PLAN 原文不改，D-048 惯例）。
  - **★ 这条口径的成立前提是「整轨 ≤ `demuxer-max-bytes`」。超过之后口径不是失效，而是窗口变长。** 立体声 DSF 负载恒定 705 600 B/s，mpv 的缓存计账比实测 **1.0647**（12 个连续采样，min 1.0646 / 中位 1.0647 / max 1.0647，取自整轨已缓存后的稳态），故有效字节率 751 252 B/s。
    - **模型**（`B` = `demuxer-max-bytes` ÷ 有效字节率；`R` ≈ 20.6 = DST 2ch 交付速度，倍实时；播放中 位置 ≈ 墙钟 `t`）：

      ```
      缓存前沿(t) ≈ min( 时长 , 位置 + B , R · t )
      卡顿        ≈ max(0, 目标 − 缓存前沿) ÷ 19.65
      铺缓存窗口（对轨尾目标）= max( 时长 ÷ R , 时长 − B )
      ```

      三项取最小值：`时长` 是天花板，`位置 + B` 是缓存容量的钉子，`R · t` 是「还没读到那么远」。**第三项不能省**——见下面 A-1 的实测。窗口内卡顿随 `t` 递减，窗口末端归零。
    - **两个 `B` 的实测点**：32 MiB → 预测 44.7 s / **实测 44.8 s**；128 MiB → 预测 178.7 s / **实测 178.6 s**（偏差 0.03%）。跨 4 倍量程线性成立。
    - **768 MiB（B ≈ 1072 s ≈ 17.9 分钟）下的三档**（`R` 生效点 `t* = B ÷ (R−1)` ≈ 55 s）：

      | 轨长 | 时长 − B | 铺缓存窗口 | 窗口内最坏卡顿（t≈1 s 跳轨尾） | 钉子生效后（t≈t*）跳轨尾 |
      |---|---|---|---|---|
      | 20 分钟（1200 s） | 128 s | **128 s** | 60 s | 3.7 s |
      | 30 分钟（1800 s） | 728 s | **728 s** | 91 s | 34 s |
      | 40 分钟（2400 s） | 1328 s | **1328 s** | 121 s | 65 s |

      **窗口长度随 `时长 − B` 线性增长，不随时长本身**；而「窗口内最坏卡顿」出现在 t→0（此时前沿被 `R·t` 压着，与 `B` 无关），约等于 `时长 ÷ 19.65`。上一版把最坏值写成 `(时长 − B) ÷ 19.65`，那实际是**钉子生效之后**的量级，不是最坏值。
    - **一句话**：「窗口过后就好」**两侧都成立**，变的只是窗口长度——整轨装得下时窗口 = `时长 ÷ 20`，装不下时窗口 = `时长 − B`。

    - **点亮的时刻错**：指示器亮在**画面恰好出来的那一毫秒**，而它读到的「缓存空」快照属于**同刻刚开始的下一次 seek**，不是刚结束的那次等待。判据在拖动这种「seek 首尾相接」的场景下会把后一次的开始误读成前一次的未完成。
    - **熄不掉**：`tickBufferWatch` 在 `waited < 300 ms` 时**直接 return，不熄灯**；拖动中 seek 每 30–50 ms 一次，`waited` 永远够不到 300 ms，于是一旦点亮就只能等拖动结束。这才是 392 ms 的一次误判膨胀成 **1.37 秒**闪烁的原因。

    - **平滑度**：相邻 read 间隔 min 3 / 中位 **4** / max 6 ms。以 150 ms 轮询取样，每格之间有约 35 次 read，进度条不会跳格。
    - **结论**：`progress = (当前 read offset − seek 时 offset) / (目标 offset − seek 时 offset)` **成立**。目标 offset 由 `目标秒 ÷ 时长 × dsf_size` 直接算得——DSF 是线性映射，这正是 D-037 当初关闭「透传 DST」时守住的性质。
    - **不需要动协议。** 字节从我们自己的 `stream_cb` 过，跨线程按 D-042 的先例用原子量 + GUI 侧轮询即可。**顺带更正一句上一轮汇报里的措辞**（检索范围：`docs/DECISIONS.md` 全文，D-066 条目内无「协议」「先报」「冻结」字样，故**该错误表述没有进条目**，只出现在汇报正文）：按 **D-036**，本项目明文冻结、发布后不可变更的只有**碟片指纹规范（D-008 / D-024）**，helper 协议 v1 可以扩展；说「改协议须先报」是把冻结范围记错了。
    - **★ 本条里的实测数据（公式、offset 序列、14.2 MB/s、平滑度）完整保留，M2 立项时不必重测。**
    - **★ 实现时须 clamp**：上表最后一格 progress 走到 **100.7%**，说明按「目标秒 ÷ 时长 × dsf_size」算出的目标 offset **略微低估**——`dsf_size` 是由碟内声明时长推出、按 4096 字节块多退少补的（D-038 记的「时长与碟内声明相差 < 6 毫秒」即此），所以实际读到的字节会略微越过算出来的目标。进度值必须 clamp 到 [0, 1]，否则条会走过头。
    - **工作量估计**：`SacdStream` 加两个 `std::atomic<int64_t>`（最近一次 read 的 offset、当前流的 size）并在 `streamRead` 里更新；`PlayerController` 武装时抓一次基准 offset 与目标 offset，轮询里算比值；QML 把转轮换成带进度的环。约 60–90 行，无新依赖、不动协议。**限制**：这条路只覆盖 `sacd://`（字节经我们自己的流层）；普通文件与碟类没有这个量，仍只能用不确定式，所以 UI 要保留两种形态。**本轮不实现。**

  - **★ 直通的归因护栏（K-0，修了一个真误判）**。D-070 的处理是「打开直通 1.5 秒后 AO 仍开不起来 → 归因直通、自动关回去」。用外部进程抢占音频设备（CoreAudio hog mode）造出「AO 本来就不通」的状态后实测：**它会误判**——弹「打开直通后音频输出打不开，已自动关掉直通」，**并把用户刚打开的开关静默关掉**，而真凶是别的应用。
    - **护栏做在「打开之前 AO 通不通」上**，但**这个量 mpv 问不出来**：设备被 hog 时 `current-ao` 照样报 `coreaudio`、`audio-out-params/format` 照样有值（实测两者都判「健康」），而播放**卡死在 0.000**（12 秒只推进 1 条进度，正常是 12 条）。唯一能分辨的量是**位置有没有在推进**——音频在放，时间就在走。故改用「最近一次位置推进距今 < 1.5 秒」当判据（暂停时按「说不准」处理，保守不动开关）。
    - **修后 A/B**：外部占用组 → `打开直通前 AO 健康=0`，弹中性文案「音频输出打不开，可能被其它应用独占；这与直通开关无关」，**开关保持在「开」**；设备正常组 → `健康=1`，正确归因、自动关回、弹原文案。
  - **★ 裸克隆构建演练（K-1，T7 核心验收口径，真做）**。全新目录从 `origin` clone，**只用 README 写的命令**，每一步一次通过，**README 无需修改**：
